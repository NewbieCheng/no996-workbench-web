## 1. 结论摘要

### 1.1 这次为什么失败

`定稿仍有未解除的硬校验问题：第一、总字数 289` 是**两条命中**用 `、` 拼在一条消息里，不是"第一项：总字数 289"：

| 命中 | 含义 |
|---|---|
| `第一` | 稿里出现「第一…」，且不在序数白名单内（白名单缺「个、时间、反应」等） |
| `总字数 289` | 120 秒目标 500 字时偏短 42%；若选 60 秒则是超上限 1.5 字 |

失败链：预填步骤只给 512 token（思考吃掉额度）→ 截断降级为写死的人群/卖点 → 稿子偏短 → 硬校验两条都不过 → 评审拿不到"哪一段要改" → 编辑拿不到"差多少字" → 三轮必然收敛不了 → 定稿抛错、稿子整份丢弃。

### 1.2 是后端、后端调用还是前端

**触发是前端，但后端确实存在一个与"长输出"有关的硬上限。**

| 判断 | 结论 |
|---|---|
| 预填 512 token 被截断 | 前端问题（`src/agent/models.ts`） |
| 字数总闸不可修 | 前端问题（硬校验与提示词） |
| 定稿丢稿 | 前端问题（流程编排） |
| `max_tokens` 被收敛到 8192 | 后端运行时设置；本次事故与它无关，但长直播会撞上 |
| 上传资料过大 | 前端没有输入闸；后端不校验输入长度，上游直接 400 |

### 1.3 后端上限能不能放宽

能，而且**不用改代码、不用重启**：`t_llm_gateway_setting.max_tokens_cap` 是运行时设置。

已核实的生产事实（2026-10-28 只读查询）：

| 项 | 值 |
|---|---|
| 当前 `max_tokens_cap` | **8192** |
| 默认聊天模型（`auto_route_model_code`） | `mimo-v2.6-flash`（小米） |
| 该模型上下文窗口 | 1,048,576 token |
| 该模型最大输出 | **131,072 token** |
| 聊天路由链头 | `deepseek@deepseek-flash`（deepseek-flash 最大输出 384,000） |
| 后端库账号权限 | `app@127.0.0.1` 对 `intelligent_team.*` 有 **ALL PRIVILEGES**（可 UPDATE） |
| SSH | 已可免密登录 `root@118.196.106.85`，`no996-backend.service` 运行中 |

**结论：16384 确实偏小，计划提到 32768**（约为默认模型最大输出的 1/4，足够 2 小时直播单章，又不至于一次调用失控）。同时给网关加"按模型上限收敛"：取 `min(全局上限, 该模型 max_output_tokens)`，避免把只支持 4096 的模型（如 `XiaomiMiMo/MiMo-V2-Flash`）打爆成 400。

## 3. 前端 A：事故修复（P0）

1. **违禁词按段展开命中**：同一个词出现在多段时每段各一条命中；`mustFixIds` 收全，不再只认第一段。
2. **修「第一」误判**：扩充序数/量词白名单（个、种、位、眼、层、句、段、届、场、局、期、年月日周季、时间、反应…）+ 宣称语境黑名单（销量/排名/行业/全国/全网/市场/品牌/口碑 + 第一，第一品牌/第一名/第一梯队）。正常叙述放行，真极限宣称仍命中，补断言。
3. **统一字数口径**：总闸与单段预算都按「口播字数」（去空白与标点）；命中说明写成「目标 500 字（合格区间 425–575），当前 289 字，还差 136 字」。
4. **评审拿到必改段**：把 `mustFixIds` + 逐段命中明细一起给评审，修掉提示词里那句不成立的描述。
5. **编辑拿到字数总账**：目标/区间/当前/差额 + 逐段预算与现状；有全局字数命中时自动把超额最多（或欠最多）的 2–3 段并入 targets，并明确「只改这些段，合计落进区间」。
6. **停止条件补硬校验**：硬校验未过且不是最后一轮时，不允许因留存达标提前退出。
7. **定稿不再丢稿**：`pass=false` 也交付；`stopReason` 写「定稿仍有 N 处待修改：…」；任务标记成功但 `meta.hardCheck=1`，成功提示改为「脚本已生成，有 N 处待修改（总字数 289）」。页面已有的红徽章 + 命中清单复活。
8. **预填限额**：`autofill` 512 → 2048（截断重试 4096），消除"模型输出被长度上限截断"。
9. **重试语义**：定稿不再失败后死循环自然消失。

### 4.2 资料上传限制（回答"上传太大怎么办"）

| 限制 | 默认值 | 行为 |
|---|---|---|
| 单份文档文件大小 | 4 MiB（沿用） | 超出直接拒绝 |
| 单份文档**正文**字数 | **50,000 字** | 超出拒绝，提示「单份资料最多 5 万字，请拆分或精简」 |
| 单次请求资料总字数 | **80,000 字** | 超出按顺序截断，并在提示词与界面同时标注「资料已截断，仅使用前 N 字」 |
| 单次附件数量 | 8（沿用） | 超出拒绝 |
| 支持的格式 | txt / md / docx（沿用） | — |

说明：这些是"能真实执行"的输入闸。账号级"每天最多生成多少次"需要服务端计数（后端已有积分与用量体系），本轮**不做假的本地计数**，列为后续项。

## 5. 前端 C：四类创作目的升级（P2）

### 5.1 目的与结构

| 创作目的 | 四套结构 |
|---|---|
| 获客型 | 人群点名型 / 问题诊断型 / 结果前置型 / 场景急救型 |
| 人设型 | 经历转折型 / 选择与原则型 / 工作幕后型 / 踩坑复盘型 |
| 观点·干货型 | 反常识论证型 / 步骤教学型 / 错误与正确对照型 / 问题拆解型 |
| 转化型 | 痛点解决型（PAS）/ 交付演示型 / 疑虑答疑型 / 价值递进型（AIDA） |

每个结构 5 段，带段名、职责、占比、适用情境、开头参考；宿主锁定，模型只展开不选择。

### 5.2 按目的收集素材（复用现有字段，只加缺的）

| 目的 | 必填 | 选填 |
|---|---|---|
| 获客型 | 目标人群、具体问题、真实解决方式/第一步、真实沟通入口 | 案例/交付物、业务阶段、场景细节 |
| 人设型 | 想呈现的一个特点、一件真实事件（背景+选择+结果） | 本人原话、可公开范围 |
| 观点·干货型 | 主题/问题、核心判断、依据或步骤 | 真实案例、明确标记的假设示例、适用边界 |
| 转化型 | 实际交付、适合对象、唯一行动入口 | 不适合对象、价格与条件、可展示证据、主要顾虑 |

提交前检查：缺必填项 → 留在当前步骤、列出待补字段、**不调用模型**。

### 5.3 生成流程（8 阶段语义）

预填（只补通用建议）→ 策划（整理事实与缺项，不改目的结构）→ 结构（展开用户所选，宿主锁定）→ 编剧（注入所选目的方法 + 预算）→ 硬校验（方案 A）→ 评审（按目的口径）→ 编辑（≤3 轮，字数总账）→ 定稿（交付不丢稿）。

### 5.4 页面

步骤二：目的四卡（获客/人设/观点·干货/转化），选中后才显示该目的的四套结构 + 自定义；未选目的或结构不能生成。切换目的清空结构、保留共用素材与各目的草稿。步骤三按目的显示素材字段。左侧预览轨显示目的/结构/段落/时间。结果页与 Markdown 模板不变。

### 5.5 兼容

- 旧 `流量` 任务：原样展示，继续生成时要求重选目的（不暗中归类）。
- 旧 `成交` 任务：按转化型生成并在界面明示「旧目标已映射为转化型」。
- 旧结构名与旧结果不迁移、不改写；Markdown 字段不变。

8. 生产：改库后调用一次长输出（如 2 小时直播）观察不再被 8192 截断。

## 13. 上线与回滚

### 13.1 顺序

1. 后端发布（含迁移 000052）：`build-release.sh` → 上传 → `migrate up` → 重启 `no996-backend.service` → `/health/ready` 返回 schema 52。

### 13.2 回滚

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 全局上限调到 32768 后，小模型被请求超限 | 上游 400 | 后端按 `max_output_tokens` 收敛；未配置的模型保持原行为 |
| 目的必填项太多，用户放弃 | 转化下降 | 必填只覆盖"没有就必须编造"的字段；其余选填；缺项提示具体到字段 |
| 四类目的改变现有历史语义 | 老用户困惑 | 旧值只读展示；生成时要求重选并明示映射 |
| 资料 8 万字上限仍不够 | 用户想喂更大资料 | 常量集中管理，后续可调；真正的超大资料应走检索而不是全量塞提示词 |
| 定稿改为交付被误读为"全通过" | 合规风险 | 红徽章 + 命中清单 + 任务提示明确写"有 N 处待修改" |
| 后端发布窗口 | 迁移未跑导致 503 | 迁移与二进制同包发布；`/health/ready` 检查 schema 52 |

## 15. 最终采用的取值

| 项 | 取值 |
|---|---|
| 后端 `max_tokens_cap` | **32768**（默认值 + 迁移 000052 + 生产库已改） |
| 前端截断重试上限 | 32768 |
| 预填 max_tokens | **8192**（按你的要求；截断重试 16384） |
| 长直播单章 max_tokens 上限 | 16384 |
| 单份文档正文字数上限 | **50,000 字**（超出直接拒绝） |
| 单次请求资料总字数上限 | **80,000 字**（超出截断并留标记） |
| 单次附件数量 | 8 |
| 未选目的/结构 | 禁止生成（提交前校验，不调模型） |
| 旧 `流量` 任务 | 生成时要求重选目的 |
| 旧 `成交` 任务 | 生成时按转化型并明示 |

### 15.1 实施偏差（与 v2 计划的差异，均在安全侧）

1. **单份资料超限改为直接拒绝**，不做截断：截断一份长文档更容易让模型把残句当成完整事实；拒绝并提示「拆分或精简」更可预期。
2. **单次合计超限仍截断**：给最后一份文档保留头部并在正文里写明「资料已截断，仅提供前 N 字」，模型与界面都能看到。
3. **后端额外加了按模型上限收敛**（`applyModelMaxOutputTokens`）：全局 cap 调高后，只支持 4096 输出的模型不会被请求打爆成 400。
4. **顺带修复了工作区里两处会让 `typecheck` 失败的历史遗留**：`src/api/tools.ts` 重复定义、`StepSearchCollect.tsx` 的重复声明。与本需求无关，但不修就无法验证。
